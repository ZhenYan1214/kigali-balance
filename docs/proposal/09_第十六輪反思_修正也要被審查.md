## 一、結論先講

1. **第十五輪的 High 修正本身有漏洞。** 〔已查證〕
   - 第二個獨立的安全審查者只拿到修正後的程式碼，不知道上一輪找到什麼。它用概念驗證測試證明了以下攻擊：
     1. 未知來源冷媒灌進設備。
     2. 回收出來時是 C 級批次。
     3. 把這個批次再灌回去（灌注時不再被標記為未知來源）。
     4. 等 180 天後回收，它就變成 A 級，可以銷毀並申請碳權。
   - 每個簽章都是真的，設備持有者只看到一次「維修」。
   - 修正方式：從設備出來的批次帶著「未知來源」標記，分割時繼承，再灌注時會重新標記。
   - 教訓：**修正也要被審查**，而且要由沒有前情的人來審。
2. **其餘可修的合約風險都修了：**
   - 只有設備登錄的維修公司能灌注（F2）；
   - 銷毀廠指定哪個註冊處能認領（F10）；
   - 治理成員可輪替、提案 30 天到期、可撤回同意、合約本身不能占席位（F11、S4、S5）；
   - 設備持有者可轉移，遺失金鑰時由治理改指定（F12）；
   - 被撤銷的金鑰不能再轉移設備或指定註冊處（S2）；
   - A 級設備必須有安裝日期（S3）；
   - 治理參數有下限，不能把規則關掉（S6）。

   模擬器加入兩種新攻擊（競爭對手灌注、未被指定的註冊處搶先認領），差異測試 7,359 筆全部一致。〔已查證〕
3. **GS1 EPCIS 2.0 從一句話變成實作。** 〔已查證〕
   - 每個批次的來源鏈都能匯出成 EPCIS 2.0 JSON-LD：1,282 個批次、15,327 個事件。
   - 全部通過 GS1 官方 2.0.1 JSON Schema 驗證，數量逐公克和帳本對帳。
   - 來源護照頁可以下載範例。
   - CBV 沒有「再生」「碳權認領」的詞，這些用專案自己的命名空間，README 有寫清楚。
4. **重新部署的路已經鋪好。** 部署腳本在本機鏈上用新合約完整跑過：六個 Demo 步驟成功，該擋的都擋下來。〔已查證〕
   使用者只要在有 `.env` 的電腦上執行即可。

## 三、還沒做、可能錯的地方

- **測試網仍是舊合約。** 這是目前最大的落差，需要使用者重新部署。
- **剩餘風險還有這些：**
  - 鋼瓶 ID 可被搶先占用；
  - B 級月上限按位址計算，也用固定時段；
  - 「一張照片一台」只比對雜湊；
  - 在途批次在寄件方被撤銷後仍可收貨；
  - 7 天內舊同意書在持有者轉回時會恢復有效。

  附件 B.2 都寫了。
- **第二次審查也是模型。** 兩輪都找到 High，代表合約還需要第三方真人稽核。附件已寫成正式上線的前提。〔推論〕
- **未知來源標記採保守做法。** 被隔離的整個批次都會被標記，可能連帶標記同一批中最近灌入、來源有文件的公克數。方向是保守的，但會讓少數合法冷媒永遠不能申請碳權。〔推論〕
