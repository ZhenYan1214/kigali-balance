# 第十四輪反思：外部裁判與真正的結果（2026-10-17）

> **觸發**：使用者再次請我讀 Felix Rieseberg〈How to be more ambitious: a tutorial for humans with models〉，反思並優化。第十三輪（`06`）已用過同一篇文章，所以這一輪要回答兩個問題：第十三輪的方案做到哪了？用文章的標準看，現在還有什麼不夠有野心？
>
> **標記**：〔已查證〕＝讀過原文或實際跑過；〔推論〕＝我的判斷。距離截止 2026-10-25 22:00（台北）還有 8 天。

---

## 一、結論先講

1. **深度進步很多，高度幾乎沒動。** 第十三輪定下的「真正的結果」有三層：前三名、至少一位真實領域人士說有用、長期試點。第二層到今天仍然是 0：五封信還在草稿資料夾，儀表板還沒對外公開，所以就算寄信，對方也沒有東西可以點開看。〔已查證〕
2. **「外部裁判」只用在規格上，沒用在「可重現性」上。** 文章說不要讓模型評自己，要用模型能跑的工具得到回饋。我們的回歸測試很完整，但**每一個數字都只在兩台 Windows 電腦上被驗證過**。昨天剛發現的換行問題就是證據：AI 模型雜湊在兩台電腦上不同，而這個雜湊是要寫上鏈、讓評審驗證的。一台乾淨的 Linux 電腦，以及一個沒有任何前情的讀者，是我們還沒用過的外部裁判。〔已查證〕
3. **AI 的成績仍然建立在一個我們自己已經證明是錯的假設上。** 第十三輪的洗白容量模型（`04`）指出：模擬器假設誠實設備報廢時「幾乎滿載」，但 IPCC 表 7.9 說小型設備報廢時只剩 0–80%、中大型 50–100%。在模擬器的假設下，同一個偵測器會誤報 40% 的誠實 A 級設備。README 上的 AI 成績因此偏樂觀，而這件事目前只寫在研究報告裡。〔已查證〕
4. **廣度還缺兩個現成的「別的領域」**，它們都是已有的、被廣泛使用的做法，可以直接拿來支撐我們的設計〔推論，待查證後引用〕：
   - **ISO 22095:2020 監管鏈模型**：身分保留、隔離、質量平衡、帳簿與宣稱。我們的「來源類別不可互換」就是其中的「隔離」模型，而不是爭議最大的「質量平衡」。對標準背景的評審，這是一句就能講清楚定位的話。
   - **加密貨幣交易所的「儲備證明」（proof of reserves）**：用 Merkle-sum 樹或承諾值，讓外人驗證「總量對得上」，又不公開每個帳戶的餘額。這正好回應「公開鏈看得到商業數量」的批評，也替第十三輪的 D（保密守恆）找到被業界大量使用的先例。
5. **必交的東西還沒開始**：英文 PDF 附件、3 分鐘影片、Devpost 說明。文章說 Presentation 是「讓忙碌的人相信一個因果故事」，影片就是那個故事，現在是零分起跳。

## 二、用文章的四個做法逐一檢查

| 文章的做法 | 我們做到的 | 還缺的 |
|---|---|---|
| **高度：交代結果，建立能自己運轉的流程** | `rebuild.py`、`check_submission.py` 一鍵重建與檢查 | 流程只在本機跑。沒有一台獨立的機器在每次推送時自動驗證；評審看不到「這些數字是被獨立重跑過的」證據 |
| **深度：外部裁判** | 真實註冊處資料稽核；洗白容量模型抓到我們自己的修正錯誤；差異測試 | 可重現性沒有外部裁判；AI 只在我們自己的模擬器上評估；沒有任何真人回饋 |
| **深度：不合理的目標** | 沒有明確設定 | 例如：**「任何評審在一台乾淨的電腦上，5 分鐘內能獨立驗證 README 上的任何一個數字」**。這個目標會逼出 CI、可攜性修正、更好的文件 |
| **深度：用原始資料檢驗假設** | 稽核用了真實資料 | 模擬器的「接近滿載」假設已被 IPCC 表推翻，但模擬器和 AI 評估還沒跟著改 |
| **廣度：把名詞換成動詞** | 第十三輪做過：「讓互不信任的各方對同一公斤的去向達成可驗證的共識」 | 這個動詞直接指向兩個成熟領域：ISO 22095 監管鏈、交易所儲備證明。還沒引用 |
| **廣度：跨領域團隊，其中要有紅隊** | 第十二輪有紅隊 | 沒有「第一次看到這個專案的人」。文章說的讀者是忙碌的評審，他們不會讀 HANDOFF |
| **廣度：做專業工作，不要角色扮演** | — | 影片要用記者的方法：從一個具體的批次講起，而不是功能清單 |

## 三、這一輪的方案

| 代號 | 做什麼 | 對應 | 誰做 | 估計 |
|---|---|---|---|---|
| **G** | **乾淨的 Linux 環境重現**：在 Docker 容器裡從零開始 clone，跑 `rebuild.py --full`，任何一個數字對不上就是發現 | 外部裁判（機器） | 我 | 半天 |
| **H** | **沒有前情的讀者重現**：開一個完全不知道這個專案的代理，只給它 GitHub 網址和 README，請它在暫存資料夾照著做，記下每一個卡住的地方和花的時間 | 外部裁判（讀者） | 我（開代理） | 平行進行 |
| **I** | **持續整合（GitHub Actions）**：每次推送都在 GitHub 的 Linux 機器上跑完整重建與交件前檢查，README 放上通過狀態的徽章；同時用 GitHub Pages 自動發布儀表板 | 高度：自己運轉的流程；把 G 變成永久的 | 我寫設定，**推送與開啟 Pages 要使用者同意** | 半天 |
| **J** | **模擬器改用 IPCC 表 7.9 的報廢剩餘量**，加入 A 級灌水造假與 A 級訊號，在全新的種子上重新評估 AI，README 的成績如實更新（大概會變差） | 深度：用原始資料檢驗假設 | 我 | 1 天 |
| **K** | **英文 PDF 附件**，加入 ISO 22095 對照、儲備證明的類比、稽核與洗白容量結果、威脅模型、已知限制 | 廣度＋必交 | 我 | 1.5 天 |
| **L** | **影片**：記者寫腳本（從一個具體批次講起）→ 編輯刪到 3 分鐘 → 做空者紅隊挑刺 | 廣度＋必交 | 我寫腳本，**使用者錄製** | 1 天 |
| **M** | **使用者今天就能做、而且最影響「真正的結果」的事**：開啟 GitHub Pages、寄出專家信件（儀表板公開後）、重新產生 Alchemy 金鑰、同意 OP Sepolia 重新部署 | 高度 | **使用者** | 1 小時 |

**順序**〔推論〕：G、H 今天平行做（它們最便宜，而且會告訴我們 I 和 K 要修什麼）→ I → J → K → L → 10/24 先送出。D（保密守恆展示）只在進度超前時做，改用「儲備證明」的框架說明。

## 四、這份反思可能錯在哪裡

- **G、H 可能什麼都沒找到**。那也是好結果：README 就能寫「在乾淨的 Linux 機器上獨立重現」，這是一句有證據的話。
- **J 會讓 AI 的成績變差**，可能有人覺得不划算。但第十二輪紅隊已經說過：冷媒背景的評審第一個問題就是回收量怎麼限制、誠實設備報廢時剩多少。成績變差但假設正確，比成績漂亮但假設被專家一眼看穿好。
- **ISO 22095 與儲備證明的說法要先查證原文再寫進交件文件**，現在只是方向。
- 這一輪仍然是模型在評模型。真正能打破這一點的只有 M：真人專家的回覆。那要靠使用者寄信。
